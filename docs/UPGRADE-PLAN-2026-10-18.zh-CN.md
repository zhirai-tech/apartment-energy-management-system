## 1. 目标与原则

### 1.1 目标（按你的要求排序）

1. **保留现在的前端 UI**（页面风格、布局、交互都不变，只做增量）。
2. **保留现有小米云登录跳转体系**（账号密码/邮箱验证/浏览器验证/国内+德国双区域），把它稳住，作为兜底通道。
3. **智能空开本地化**：功率、电流、电压、累计电量、开关控制全部走局域网，断网/云挂/风控时照常工作。
4. **新增 ONVIF 局域网摄像头**：发现/添加/直播/录像/回放/监控墙，完全本地。
5. **旧小米摄像头稳定化**：从"云端 HLS 代理"切换为"go2rtc 本地 P2P 优先"，云端只做兜底。
6. **项目结构整理**：前端 / 后端 API / 设备接入 / 流媒体 / 部署分开，每个系统独立构建与运行。
7. **部署到局域网那台空闲电脑**：单机、开机自启、可备份、可回滚。

### 1.2 设计原则

- **本地优先，云端兜底**：能用局域网协议的设备永远先走本地；本地失败才降级到小米云，并在 UI 明确标注"本地/云端/离线"。
- **保留登录体系不动**：小米账号登录相关页面与流程原样保留，只增强会话稳定性与降频。
- **UI 只加不改**：现有页面结构、组件风格、路由都保留；新增"设备接入/摄像头添加"等页面作为补充。
- **前端不感知设备来源**：无论数据来自小米云、本地 MiIO、ONVIF，前端拿到的都是统一的设备/摄像头/读数模型。
- **渐进式重构**：每个阶段结束都能构建、能部署、能回滚；不做一次性推倒重写。
- **不引入 Home Assistant 运行时**：只借鉴它的接入架构；避免多维护一套系统（如你以后想接 HA 设备，再加 MQTT 桥）。

### 2.3 设备接入契约（核心抽象）

```ts
// packages/core/src/provider.ts
export type ProviderId =
  | 'xiaomi-local' | 'xiaomi-cloud' | 'onvif'
  | 'http' | 'modbus' | 'tuya-local' | 'mqtt';

export interface DeviceProvider {
  id: ProviderId;
  /** 发现设备：局域网扫描 / 云列表 / ONVIF 发现 / 手动添加 */
  discover(ctx: DiscoverContext): Promise<DiscoveredDevice[]>;
  /** 读取状态与遥测（在线、开关、功率、电流、电压、累计电量、温度…） */
  read(device: DeviceRef): Promise<DeviceReading>;
  /** 控制：开/关/重启等 */
  control(device: DeviceRef, cmd: DeviceCommand): Promise<ControlResult>;
  /** 摄像头类：返回本地可播放流（go2rtc 流名/RTSP/ONVIF 地址） */
  getStream?(device: DeviceRef): Promise<StreamSource | null>;
}

export interface DeviceReading {
  online: boolean;
  power?: boolean | null;
  metrics: Record<string, number | null>; // powerW / voltageV / currentA / totalKwh / temperature…
  source: ProviderId;      // 本次数据来源（本地/云端）
  latencyMs?: number;
  error?: string;
}
```

数据库改动（**只增字段，不动现有数据**）：
- `Device` 增加：`provider`（默认按现有数据推断）、`miioToken`（加密存储）、`capabilities Json`、`lastLocalReadAt`、`localOnline Boolean`。
- 新增 `DeviceTelemetry`（`deviceId, metric, value, unit, ts`）——为将来的温湿度等传感器准备。
- `DeviceCategory` 扩展：`temp_humidity_sensor / door_sensor / water_leak_sensor / energy_meter` 等（先加枚举，UI 后续用）。

## 3. 关键技术方案

### 3.1 智能空开本地化（miIO / MIoT LAN）

| 步骤 | 说明 |
|---|---|
| ① token 提取 | 在现有小米云同步流程中，从 `home/device_list` 的返回里保存每个设备的 `token`（32 位 hex）。用 AES-256-GCM 加密后存 DB（密钥放服务器本地文件/环境变量，不进仓库）。 |
| ② 协议实现 | `provider-xiaomi-local`：UDP 54321 握手；`key = MD5(token)`，`iv = token`，AES-128-CBC；报文头 `0x2131` + 长度 + 设备 DID + 时间戳；支持 `miotspec/prop/get` / `miotspec/prop/set` / `miotspec/action`。 |
| ③ 读数据 | 每台每 2–5 秒批量读：`siid=2,piid=1`（开关）、`siid=3,piid=1`（累计电量）、`3/2`（电流）、`3/3`（电压）、`3/6`（功率），复用现有单位换算。10 台 × 5 个属性 = 一次并发 UDP 即可，毫秒级。 |
| ④ 控制 | 本地 `siid=2,piid=1 = true/false` → 回读确认 → 写操作日志 → socket 推送；失败自动降级小米云并标注。 |
| ⑤ 断网降级 | UI 设备卡增加"数据来源"角标：`本地`（绿）/`云端`（黄）/`离线`（灰）。断网时本地数据照常刷新，云端字段显示"云端不可用"。 |
| ⑥ 兜底 | 本地连续失败 N 次 → 自动切云端轮询（低频）；本地恢复 → 自动切回。 |

> 已验证：10 台空开在局域网内均可握手；型号属性映射在现有代码中已存在（`lxzn.switch.cbcsmj`）。

### 3.2 ONVIF 局域网摄像头

| 步骤 | 说明 |
|---|---|
| ① 发现 | 后端实现 WS-Discovery（UDP 组播 239.255.255.250:3702，SOAP Probe），并支持**手动填 IP + 账号密码**添加（最稳）。 |
| ② 探测 | 对目标 IP 调 ONVIF `GetDeviceInformation` / `GetProfiles` / `GetStreamUri`，拿到主/子码流 RTSP 地址；失败则回退到常见品牌 RTSP 模板（海康 `/Streaming/Channels/101`、大华 `/cam/realmonitor?channel=1&subtype=0`、TP-Link/Tapo `/stream1`）。 |
| ③ 注册流 | 调 go2rtc `PUT /api/streams?name=zaem_<did>&src=<rtsp或onvif地址>`（动态注册，不再手改 yaml）。 |
| ④ 播放 | 后端代理：`/api/device/<did>/camera_stream` 返回 `/streams/hls/...`（后端再反代 go2rtc `/api/stream.m3u8?src=zaem_<did>`），前端 `hls.js` 完全不用改。 |
| ⑤ 快照 | 后端反代 go2rtc `/api/frame.jpeg?src=zaem_<did>`，用于房间卡片与监控墙缩略图。 |
| ⑥ 录像 | ffmpeg 从 `rtsp://127.0.0.1:8554/zaem_<did>` 拉流录制（复用现有录制/回放页面与计划引擎）。 |
| ⑦ 监控墙 | 统一摄像头列表：`小米(本地/云) + ONVIF` 都从数据库读取，来源标注；现有 `CameraWallPage` 只改数据源和加"添加摄像头"入口。 |

> go2rtc 已在你服务器上运行（1.9.14），无需新增组件；ONVIF 客户端和动态 API 都是其内置能力（已核对官方 API 文档）。

### 3.3 旧小米摄像头稳定化

1. 保留现有小米账号登录/跳转体系与双区域（`main` 国内、`camera` 德国）不变。
2. 登录成功后，把小米摄像头账号的 V1 token 通过 go2rtc `PATCH /api/config` **动态注入**（不再手写 `go2rtc.yaml`，仓库和磁盘上都不出现真实 token）。
3. 摄像头优先用 go2rtc 本地 `xiaomi://` P2P 流（你现在的 `cam` 就是这么跑的）；只有 go2rtc 拉流失败时才降级到云端 HLS 代理（现有代码保留作兜底，但不再是默认路径）。
4. 每次连接需要联网换取密钥（go2rtc 官方限制），这一点在 UI 上说明，不影响本地网络内观看。
5. 删除手工维护 yaml 的做法，改成"DB 里配账号 + 后端自动同步到 go2rtc"。

### 3.4 小米云稳定化（保留登录跳转，只做稳）

| 问题 | 方案 |
|---|---|
| 每分钟全量云同步 + 页面 15s 触发全量刷新 | 本地化后云端降为**每 5–10 分钟一次**（可配置）；页面请求只读缓存，不再触发云端全量；空开数据全部来自本地 |
| 主账号 401 无自动恢复 | 补齐单飞 + 指数退避 + 5 分钟限频；失败写告警中心并在 UI 显示"云端登录失效，请重新验证"，本地数据不受影响 |
| 双区域（国内/德国）混用 | 明确"账号-区域-用途"配置：`main=cn（空开）`、`camera=de（摄像头）`；登录页保留区域选择；不允许跨区域复用会话；UI 显示每个账号的区域与状态 |
| 错误被吞 | 移除业务代码里的 `catch {}` 静默；统一失败原因写入 `AlarmLog` 和结构化日志（脱敏） |
| 频率风控 | 本地化后云端调用量下降 80%+；保留"仅登录/仅兜底"两种模式 |
| 调试埋点 | 删除 21 处 `debug-point`（含外网上报地址）；这部分代码在生产部署也会执行，必须清掉（与测试服务器本身无关） |

### 3.5 流媒体层（go2rtc + ffmpeg）

- `packages/streaming` 封装：`ensureStream(name, src)`、`removeStream(name)`、`getHlsUrl(name)`、`getSnapshot(name)`、`health()`、`listStreams()`。
- go2rtc 只监听 `127.0.0.1:1984`（现在对局域网开放，存在被同网段任意设备调用 exec 模块的安全风险）；后端统一代理并加认证。
- 录像：ffmpeg 从 go2rtc RTSP 拉流 → HLS/MP4 落盘（复用现有录制/计划/回放逻辑，只换源地址）。
- 保留现有"云端 HLS 代理"代码作为最后兜底，但默认关闭。

### 3.6 前端（保留现有 UI）

**不动的部分**：仪表盘、房间卡片、图表、房间详情、告警中心、操作日志、录像回放、导出、登录页、整体视觉与组件库。

**新增/调整的部分**：
1. `系统设置` 页拆分（现在 2442 行 4 大块挤在一起）：
   - 系统参数（不变）
   - 设备总览（不变）
   - **设备接入**（新）：小米账号（国内/德国）、局域网空开（本地/云端/离线状态、批量绑定 token、测试读数）、ONVIF 摄像头（发现/手动添加/测试）
   - 账号管理（不变）
2. **添加摄像头向导**（新）：扫描发现 → 选中 → 填账号密码 → 测试画面 → 保存。
3. 设备卡/摄像头卡增加"数据来源"角标（本地/云端/离线），点击可看最后一次本地/云端读数时间。
4. 监控墙统一数据源 + 分页/分组（小米/ONVIF 混排）。
5. 摄像头详情增加"流健康"提示（go2rtc 是否在线、当前走本地还是云端）。

## 7. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| token 提取失败（部分设备云端不返回 token） | 该设备无法本地化 | 保留云端兜底；用 Mi Home 备份/token 工具离线提取；逐台排查 |
| 型号属性映射与 lxzn 不同 | 读数/控制异常 | 先做"逐台探测 + 只读验证"，映射可配置；异常设备自动回落云端 |
| ONVIF 兼容性差异 | 部分摄像头拉流失败 | 支持手动 RTSP 地址兜底；按品牌维护模板；go2rtc 日志定位 |
| 重构引入回归 | 现有功能损坏 | 每阶段构建 + 冒烟 + tag 回滚；关键业务（限额断电/自动恢复）补测试 |
| 小米摄像头 P2P 每次连接需联网 | 断外网时旧摄像头不可用 | UI 明确提示；新 ONVIF 摄像头作为主监控；旧摄像头定位为辅助 |
| 服务器/端口/服务冲突 | 部署失败 | 部署脚本预检端口与服务；支持一键回滚上一版本 |
| 数据丢失 | 业务数据不可恢复 | 迁移前备份 + 每日自动备份 + 保留期策略 |
| 双区域账号混用 | 登录被风控 | 账号-区域-用途固定配置；登录操作串行化；失败退避 |

### 11.2 登录面板：多区域登录状态显示（你的新要求）

### 11.3 小米智能空开：本地能力探测 → 本地化（已实测可本地通信）

**已确认**：`192.168.41.181 ~ 190` 共 10 台全部响应 MiIO UDP 54321 握手（返回设备 ID），本地协议可用；型号属性映射代码里已存在（开关 `2/1`、累计电量 `3/1`、电流 `3/2`、电压 `3/3`、功率 `3/6`）。

**下一步（按顺序）**：
1. **只读能力探测**（先做，约 0.5–1 天）：写一个 `probe-device` 脚本/接口，对每台设备逐项探测并输出报告：
   - 本地握手延迟、token 是否存在、支持哪些 MIoT 属性（开关/功率/电流/电压/累计电量/温度/漏电保护等）、只读是否成功、控制命令是否可下发（先不真下发，用"查询能力"方式）；

2. **token 抓取**：现有小米云同步（`home/device_list`）返回里带 token，登录一次自动保存（加密入库）。
3. **本地轮询 + 控制**：10 台并发本地读取（默认 3–5 秒），本地开关控制 + 回读确认，失败自动回落云端。
4. **UI**：设备卡显示「数据来源：本地 / 云端 / 离线」；接入页显示 10 台本地状态。
5. **验收**：拔外网 10 分钟，功率/电流/电压/累计电量与开关控制全部正常。

### 11.4 温度等更多设备（照 Home Assistant 的思路补）

- 接入优先级：① MQTT（ESPHome/Tasmota/Home Assistant 都能接，兼容面最大）→ ② 涂鸦本地（如果以后买涂鸦空开/插座/电表）→ ③ 小米温湿度（走现有小米云或本地，视型号）；
- UI：房间详情加"环境数据"小卡片 + 趋势图 + 阈值告警；保持现有卡片风格。
- 工时：模型 2 天 + MQTT 2 天 + UI 2–3 天 ≈ 5–7 天（原阶段 G，可后置）。

### 11.5 路由器 / 信号放大器识别与流量监控

**现状**：系统已有网络设备页（`NetworkDevicePage`）、华为 5G CPE / Nokia Beacon 适配器、`DailyNetworkTraffic` 流量模型、局域网扫描/厂商识别。**放大器/路由器能被扫描识别**（OUI + 名称 + 分类），但**流量监控要看具体设备支持什么协议**。

**方案（先探测，再按型号适配）**：

| 能力 | HA 的现状 | 对我们的价值 | 结论 |
|---|---|---|---|

- go2rtc / HTTP 探测：只做 `GET /api`、`GET /api/streams` 与页面首页请求，无写入。
