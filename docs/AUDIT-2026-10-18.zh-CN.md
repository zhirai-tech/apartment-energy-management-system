## 0. 先看结论（Executive Summary）

| 问题 | 结论 |
|---|---|
| 项目整体结构是否合适？ | 分层方向合适（client / server / shared + 模块化），但**颗粒度严重失衡**：`system` 一个模块占后端 65% 代码、65% 接口，把小米账号、摄像头、流媒体、录像、局域网扫描、网络设备、系统设置全揉在一起 |
| 能不能升级？ | **能。** 而且代码里已经留好了升级接口（`Device.localip / controlProtocol / controlConfig`、`SiteAdapterType`、`EdgeNode`、`lan-scan`、go2rtc），只是还没接完 |
| 局域网摄像头现在能加吗？ | **只能"扫到 + 抓一张快照"，不能看实时画面、不能录像、不能上监控墙。** 这和你的感受一致。缺的是 ONVIF/RTSP 接入 + go2rtc 动态注册 + 前端添加向导，不是从零开始 |
| 小米云为什么老掉线/怕封控？ | 代码**每分钟做一次全量云端同步**，任何页面请求数据超过 15 秒也会触发全量云刷新；摄像头还单独用一个账号全量拉。云端会话失效后主账号**没有自动恢复**，错误又被大量 `catch {}` 吞掉，所以表现成"悄悄掉线"。这是可以大幅改善的 |
| 能不能不依赖小米云？ | 小米设备首次配对/token 仍需要一次云端授权，但**拿到 token 后可以本地直连控制**（MiIO/MiOT LAN）；小米摄像头同理，token 拿到后 go2rtc 可走本地 P2P 拉流。所以能做到"云端只做兜底"，不能做到"完全不要云端" |
| 温湿度等传感器能加吗？ | 能，但需要先泛化设备模型（现在 `Device` 表只有功率/电流/电压/累计电量，没有通用遥测字段，也没有传感器类别） |
| 需要拆成几个仓库吗？ | 建议**先单仓 + 严格包边界**（前端 / API / 接入 SDK 各自独立构建和运行），跑顺之后再考虑拆仓。理由见第 5 节 |
| 最该马上做的 3 件事 | ① 删除 21 处调试埋点（其中 7 处把你的小米账号/设备信息发到外网 IP，且已推到公开 GitHub）；② 更换生产服务器 SSH 密码、清理 `deploy/ssh-helper.ps1` 明文凭据；③ 把工作区里含真实数据的 SQL 转储 / go2rtc token 配置移出仓库目录 |

## 1. 项目现在到底是个什么项目

### 1.1 功能地图（按代码实际能力统计，不看 README）

它已经**远不止 README 里写的"电费管理"**。按代码梳理，实际能力是：

**A. 能源 / 房间管理（核心业务，成熟）**
- 房间（Room）维度：实时功率、累计电量、今日用电、日限额、月电费限额、断/复电
- 自动断电：达到 100% 日限额自动断电；80/90/95% 三级预警；次日自动恢复（可配置业务日切时间与时区）
- 统计：今日/昨日/月/年、24h/7d/30d/12m 趋势、房间排名、电费趋势
- 告警中心、操作审计日志、数据导出（Excel 类导出）
- 用户与角色：admin / boss / user，强制改密、登录限流
- 多站点（Site）/ 边缘节点（EdgeNode）模型——**但业务上基本没真正用起来，是超前设计**

**B. 小米云接入（成熟但脆弱，也是不稳定的根源）**
- 账号密码 / 会话 / 邮箱验证码 / 浏览器安全验证四种登录方式
- 双会话体系：`main`（主账号，电表/空开）+ `camera`（相机专用账号，默认欧洲区）
- 设备发现、同步入库、属性批量拉取、开关控制、命令后状态确认
- 会话存 Redis，支持手动登录续接

**C. 摄像头 / 视频（复杂度最高、最不稳定）**
- 小米云摄像头：MiOT `start_rtsp_stream` + 云端 HLS 代理（ffmpeg 转 HLS）、本地 go2rtc P2P 桥（`xiaomi://`）三级 fallback
- 实时画面、PTZ 控制、能力探测、通用控制
- 录制：手动连续录制、智能侦测录制、录制计划（布防）、录像回放
- 监控墙（多画面网格）、录制参数（灵敏度/预录/尾留）

**D. 局域网设备（半成品，正是你想补的部分）**
- 局域网扫描：多网段、TCP/UDP 探测、ARP 邻居、厂商/OUI 识别、设备分类、一键入库（`LAN_<MAC>` 作为设备 ID）
- 网络设备适配：华为 5G CPE、Nokia Beacon Mesh、路由器/AP 状态
- 局域网控制适配器：HTTP/JSON、Modbus TCP **可用**；`tuya_local`、`miio_lan` **只是占位，调用直接抛"暂未支持"**
- 已存的真实数据里已经有 `LAN_507B912C6789` 这个局域网摄像头记录 → 说明扫描/入库跑通过，但**实时流没有走通**

**E. 运维/部署**
- Docker Compose（postgres + redis + go2rtc + server + client）
- 另一套 `deploy/remote/`（server + redis + cloudflared 隧道）
- 还有一套 Windows 服务部署（TUNNEL.md：`zaem-server` / `zaem-tunnel` + Cloudflare Quick Tunnel）
- 34 个 PowerShell 脚本散落在 `deploy/`（大量一次性调试脚本）

## 2. 整体结构评估

### 2.1 现有结构

```
client/     React 前端（纯前端，独立构建）
server/     Express 后端（API + 小米接入 + 摄像头 + 流媒体 + 定时任务 + 业务逻辑全部混在一起）
shared/     前后端共享类型（但也混了 OUI 表、设备分类推断等运行时代码）
deploy/     部署 + 一堆一次性调试脚本
go2rtc/     go2rtc 程序 + 含真实小米 token 的静态配置
release/    打好的发布包 + 录像片段 + HLS 分片（7.8 MB）
docs/       只有 1 张截图，没有任何架构/接口文档
根目录       docker-compose.yml、package.json、package-lock.json、2 个 tar.gz、504 KB 数据库转储、TUNNEL.md
```

### 2.2 做得对的地方（不要动）

1. **分层大方向正确**：前端 / 后端 / 共享类型 / 部署四层齐全，是标准的全栈项目结构。
2. **业务域拆分有雏形**：`auth / dashboard / energy / logs / export / system` 六个模块，符合 DDD 的模块化思路。
3. **数据模型设计不错**：`Site / EdgeNode / Room / Device / EnergyLimit / DailyEnergy / HourlyEnergy / MonthlyEnergy / AlarmLog / OperationLog / SystemSettings`，已经考虑了多站点和边缘节点，扩展传感器时不用推翻。
4. **设备接入已经预留了抽象位**：`Device.localip`、`controlProtocol`、`controlConfig`（JSON）、`SiteAdapterType`、各 `*.adapter.ts`——说明作者（你）已经意识到要支持多协议，只是没接完。
5. **前端 UI 实际观感不差**（截图看：卡片式仪表盘、中文界面、移动端适配），没必要换 UI。
6. **安全底子部分已有**：JWT、bcrypt、登录限流、强制改密、操作审计、`.env` 未入库、`.gitignore` 覆盖了大部分敏感文件。

### 2.3 结构上的核心问题（"乱"的根源）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| 1 | **`system` 是上帝模块（God Module）** | 11,758 行 / 12 文件 / 51 个接口，含小米账号、摄像头、流媒体、录像、扫描、网络设备、站点、设置 | 改任何一处都怕碰坏别的；文件大到 AI/人都难以完整理解；这是"乱"的最大来源 |
| 2 | **集成层与业务层耦合** | `energy.service`、`dashboard.service`、`cron.ts` 直接 import `xiaomiAdapter` 和 `systemService`；能源统计强依赖小米云 | 换/加设备厂商必须改业务代码；云端一挂，统计和页面一起挂 |
| 3 | **前端巨型页面** | `SystemSettingsPage` 2442 行（系统参数 + 设备总览 + 小米同步 + 账号/局域网识别 4 大块）、`RoomCard` 2355 行 | 一个小改动要动 2000 行文件；复用困难 |
| 4 | **共享包不"干净"** | `shared/index.ts` 只有 1 个文件 1255 行：既有前后端 DTO，又有 OUI 表、`inferDeviceCategory`、网络分组等运行时代码 | 前端被迫打包后端逻辑；类型契约与工具函数边界不清 |
| 5 | **仓库根目录混放产物** | `zaem-dump.sql`（504 KB，含用户密码哈希、设备配置）、`server-dist.tar.gz`、`go2rtc.exe`(19 MB)/zip、`release/`(7.8 MB 含录像)、`deploy/` 34 个脚本 | 仓库 74 MB（不含 node_modules）；容易误提交/误分享敏感数据；新人（或未来的你）看不出哪些是源文件 |
| 6 | **三套部署方式并存** | 根 `docker-compose.yml`、`deploy/remote/docker-compose.zaem-energy.yml`、`TUNNEL.md`（Windows 服务 + Quick Tunnel） | 不知道生产到底按哪套跑；改一处忘另一处 |
| 7 | **无测试 / 无 lint / 无 CI** | 0 个测试文件、无 ESLint 配置、无 `.github/workflows` | 重构没有安全网；回归靠手工点页面 |
| 8 | **构建脚本有顺序 bug** | `server/package.json:8`：`tsc && ... && prisma generate` | 全新克隆后 `npm run build` 必失败（已实测） |
| 9 | **文档严重滞后** | README 只写了电费管理，完全没提摄像头、监控墙、录像、局域网扫描、华为 CPE/Nokia、go2rtc；没有 API 文档（Swagger 已挂 `/api/docs`，但 0 个 `@openapi` 注解 = 空页面） | "看不清整体结构"的直接原因 |
| 10 | **`any` 滥用 + 空 catch 吞错** | `system.service` 124 处 `any`、`xiaomi.adapter` 62 处；大量 `catch {}` / `.catch(() => {})` | 云端/设备出错时 UI 只表现为"掉线/没数据"，排查困难 |
| 11 | **未提交改动悬空** | 工作区 8 个文件、+1023/-343 行（摄像头流稳定性改造），未 commit | 有丢失/冲突风险；无法判断"当前部署的是哪个版本" |
| 12 | **注释/文档中英混杂、文件编码不统一** | 大量中文注释、README/CHANGELOG 英文；部分配置文件疑似 GBK 编码（`.env`、`.gitignore` 中文注释显示乱码） | 检索、协作、后续国际化都受影响（低优先级） |

### 2.4 结论

> **现有结构"方向对、颗粒度错、边界脏"。**
> 不需要推倒重写（重写 3.7 万行风险极高、收益低），应该**按域渐进拆分 + 补齐安全网（测试/CI/lint）+ 把接入层独立**。拆分过程中每一步都保持"能构建、功能等价"，随时可停。

### P0 — 安全 / 泄密，建议 24 小时内处理

**P0-2｜生产服务器 SSH 凭据明文写在已公开的脚本里**
- 位置：`deploy/ssh-helper.ps1` 第 15–17 行：主机 `192.168.41.199`、用户 `Administrator`、**明文弱口令**（此处不复述，请打开文件确认）。

- 处理（按顺序）：① **立即修改服务器密码**（并检查 22 端口是否暴露公网、是否存在其他后门账号）；② 改用 SSH 密钥 + 环境变量；③ 用 `git filter-repo` 从历史中清除该文件，强制推送（或把仓库转为私有）；④ 轮换该服务器上所有能轮换的凭据（数据库、JWT_SECRET、小米账号）。
- 注意：仅仅"删除文件再提交"不够，历史里仍然能翻到。

**P0-3｜工作目录里有含真实数据的敏感文件，且没有被 Git 跟踪（好事），但很容易被误打包/误分享**
- `zaem-dump.sql`（504 KB）：完整 PostgreSQL 转储，包含 `User`（bcrypt 哈希）、`Device`（含控制配置）、`SystemSettings`、操作日志等。
- `go2rtc/go2rtc.yaml`：含**真实小米摄像头 token 和局域网 IP**（`8305588213`、`192.168.41.153`）。
- `server/.env`：含真实小米账号密码、相机账号密码、数据库密码。`deploy/remote.env`、`deploy/hlsurl.txt` 同类。
- `release/`、`server-dist.tar.gz`、`client-dist.tar.gz`、`deploy/*.tar.gz`：构建产物 + 录像 HLS 分片（合计 20 MB+）。
- 处理：把数据转储移到仓库外并加密备份；发布包只放 `release/` 且整个目录 gitignore；`go2rtc.yaml` 改为模板 + 运行时生成；确认这些文件没被打进任何对外发布的压缩包。

**P0-4｜前端"记住密码"把明文密码写进 localStorage**
- 位置：`client/src/store/auth.ts` 第 6–9 行、第 55–64 行：`remembered: { username, password }` 被 `persist` 到 `localStorage`（key `auth-storage`）。
- 影响：任何 XSS/恶意浏览器扩展都能直接拿走账号密码。
- 处理：改为只记住用户名；密码交给浏览器密码管理器；或换 httpOnly Cookie 会话。

**P0-5｜认证与会话设计的 5 个薄弱点**
1. JWT 有效期 7 天，**无刷新令牌、无服务端吊销**（`auth.service.ts:134`）。
2. 支持 `?token=` 查询参数认证（`middleware/auth.ts:25–27`，为 HLS 视频播放在 URL 里带 token），token 会进入浏览器历史、代理日志、Referer。
3. CORS 实际配置为 `origin: true`（反射任意来源 + `credentials: true`），`CORS_ORIGIN` 环境变量被忽略了（`index.ts:25–35`）。
4. `JWT_SECRET` 缺省值 `dev_secret`（`config/env.ts:6`），生产若忘配则完全可伪造 token。
5. 默认账号 `admin/admin123`、`boss/boss123`、`user/user123` 由 seed 创建，Dockerfile 每次启动都执行 `prisma db seed`（幂等 upsert，不会覆盖已改密码，但**新部署若忘改密就是后门**）。
- 处理：短期改成 `httpOnly` Cookie + 短 JWT（15–60 分钟）+ 刷新令牌；流地址使用一次性短期签名票据；CORS 白名单化；生产启动时校验 `JWT_SECRET` 非默认值并强制改密。

**P0-6｜依赖漏洞（生产依赖）**
- `npm audit --omit=dev`：**21 个（1 critical / 11 high / 9 moderate）**。
- critical：`proxy-addr` IPv4-mapped IPv6 伪造 IP；后端 `app.set('trust proxy', 1)` + 登录限流按 IP 计数，可被绕过。
- high：`axios`（10 余个公告：原型污染、SSRF、ReDoS、header 注入等）；`socket.io/engine.io` 协议 DoS；`braces/micromatch`。
- 处理：`npm audit fix` → 升级 axios/socket.io/express 依赖 → 加 `npm audit` 到 CI。

**P0-7｜日志里打印敏感信息**
- `system.controller.ts:1804–1812`：`console.info` 打印摄像头会话 `serviceToken` 前 16 位、userId、region。
- `xiaomi.adapter.ts:1810–1831`：打印设备 DID/name/model 列表。
- `index.ts:37–43`：为排障加的摄像头 URL 全量请求日志（含 `?token=` 时会把 token 写进日志）。
- 处理：改成结构化日志 + 脱敏（保留 did 后 4 位、token 全部星号），生产默认 debug 日志关闭。

### P1 — 稳定性 / 功能 / 工程，建议 1–2 周内处理

**P1-1｜小米云调用过于频繁（掉线/风控风险的核心）**
- `server/src/lib/cron.ts`：**每分钟**执行 `syncDataTask()` → `xiaomiAdapter.refreshAllRoomsRealtime()`，内部依次 `fetchDevices()`（主账号全量设备列表 + 批量属性）+ `fetchCameraDevices()`（相机账号全量设备列表）。
- 前端仪表盘 5 秒轮询；后端 `ensureRealtimeFresh(15000)`：任何能源/仪表盘请求发现数据超过 15 秒，就再触发一次**全量**云刷新（`xiaomi.adapter.ts:3116`）。
- `energy.service` / `dashboard.service` 也直接调用云（`ensureRealtimeFresh`、`ensureDailyHistoryFresh`、`refreshAllRoomsRealtime`）。
- 估算：一天 1440 次定时全量 + 页面活跃时每分钟最多 4 次全量 → 对 10 台设备来说，云端请求量远超必要。**这是"小米云设备总是掉线"的最大可控因素。**
- 处理：可配置轮询间隔（默认 60–120 秒）；改为按设备增量拉取；页面无人使用时降频；本地控制上线后云端只做兜底。

**P1-2｜主账号会话失效没有自动恢复，错误被吞**
- `xiaomi.adapter.ts:1705`：`if (resp.status >= 400) throw ...` 在 401 判断之前，**401 分支永远走不到**（死代码）；`verifySession` 里匹配 `requestIo region=.*HTTP 401` 的正则与实际错误文本 `Xiaomi io HTTP_401:...` 不匹配，提示信息永远走 fallback。
- 只有 `camera` 会话有"单飞 + 5 分钟限频"的自动恢复（`recoverCameraSession`）；**main 会话没有**，失效后只能人工重新登录。
- 大量 `.catch(() => {})` 把失败静默掉（`cron.ts`、`system.service`），前端只看到数据不动。
- 处理：补齐 main 会话恢复（限频 + 退避 + 告警通知），删除死代码，把关键失败写入告警中心。

**P1-3｜局域网摄像头：设备能进库，但看不了实时画面**
- 现状链路：
  - `lan-scan.ts`（891 行）能扫出摄像头并识别厂商；
  - `persistLanDevices` 以 `LAN_<MAC>` 入库，带 `localip`；
  - `getDeviceSnapshot` 能按 `manualSnapshotUrl` 或常见 ONVIF/ISAPI/海康/大华快照地址抓缩略图；
  - **但** `getCameraStream`（`system.controller.ts:1287+`）只有"本地 go2rtc 桥 → 小米云 HLS 代理 → 小米云 RTSP"三条路，全部是小米设备逻辑；
  - 监控墙只请求 `/xiaomi/camera/devices`（`CameraWallPage.tsx:179–185`），局域网摄像头不会出现在墙上；
  - `go2rtc.yaml` 是静态手工配置（还写死了真实 token），没有动态注册接口。
- 结论：**"不能加入局域网摄像头"是准确的**——准确说法是：能扫描、能入库、能看单张快照，**不能直播、不能录像、不能上墙**。
- 处理：见第 4 节方案（ONVIF 发现 + RTSP 配置 + go2rtc 动态注册 + 统一摄像头列表）。

**P1-4｜局域网开关控制只完成了一半**
- `local-device.adapter.ts`：`http`、`modbus_tcp` 已实现；`tuya_local`、`miio_lan` 只有类型定义，调用时直接 `throw '暂未支持'`（第 274–277 行）。
- 也就是说：能控制"自己有 HTTP 接口或 Modbus 的可编程空开"，但**市面上常见的涂鸦系 WiFi 空开/计量插座、以及小米设备的本地直连都接不了**。
- 处理：见第 4 节。

**P1-5｜没有通用遥测/传感器模型**
- `Device` 表只有 `power / powerW / currentA / voltageV / totalKwh / lastSyncAt / offlineSince`；`DeviceCategory` 只有 `circuit_breaker / camera / wifi_ap / smart_appliance / five_g_cpe / other`。
- **没有温度、湿度、门磁、水浸、人体、通用电表等字段和类别**，也没有历史遥测表。
- 处理：新增 `capability`（能力声明）+ `DeviceTelemetry`（时序遥测）抽象，再扩展类别与 UI。

**P1-6｜工程基建缺失**
- 0 测试、0 lint、0 CI/CD、0 版本发布流程。
- 构建顺序 bug（见 1.4）。

**P1-7｜部署方式混乱**

- 处理：统一成"开发 compose + 生产 compose（含 go2rtc/ffmpeg/postgres/redis/反代）"两套，TUNNEL 作为可选接入方式写进部署文档。

## 4. 升级可行性评估（重点回答你的问题）

> 总判断：**能升，而且大部分是"接线 + 补零件"，不是"重造轮子"。** 下面按你关心的顺序逐项给现状、方案、难度、收益。

### 4.1 局域网摄像头（你最想要的）

| 项 | 内容 |
|---|---|
| 现状 | 能扫描、能入库、能抓快照；**不能直播/录像/上墙** |
| 已有基础 | `lan-scan`（扫描/厂商识别）、`Device.localip`、`getDeviceSnapshot`、go2rtc（已在跑）、`hls.js` 播放器、录像/回放页面 |
| 缺口 | ① ONVIF WS-Discovery / RTSP 地址探测；② 摄像头接入配置（RTSP 主/子码流、账号密码、传输协议）；③ go2rtc **动态注册**（`PUT /api/streams`）替代手工改 yaml；④ 统一摄像头列表（不再只查小米）；⑤ 录像源改为"设备自身 stream URL"；⑥ 前端"添加局域网摄像头"向导 + 测试/预览 |
| 方案 | 新增 `provider-onvif`：WS-Discovery 发现 + ONVIF GetStreamUri + 常见品牌 RTSP 模板（海康 `/Streaming/Channels/101`、大华 `/cam/realmonitor?channel=1&subtype=0`、TP-Link/水星等）；后端把 RTSP 注册到 go2rtc → 返回 HLS 地址 → 复用现有播放器；录像改用 go2rtc/ffmpeg 拉 RTSP |
| 难度 | 中（协议不复杂，但硬件型号兼容需要联调） |
| 工作量 | 后端 2–3 天 + 前端 2 天 + 联调 1–2 天 |
| 收益 | 彻底解决"加不了局域网摄像头"；不再依赖小米云；延迟低于云端代理 |

### 4.2 小米摄像头本地化（解决"画面一会有一会没有"）

| 项 | 内容 |
|---|---|
| 现状 | 已实现 `GET /device/:did/camera_token` 获取 MiOT V1 token；go2rtc 支持 `xiaomi://` 走本地 P2P 拉流；但 token 要手工写进 `go2rtc.yaml`，且配置里已有真实 token |
| 根因 | 现在首选"本地 go2rtc 桥"，但桥是手工配置的，配不上就退回"云端 HLS 代理"（ffmpeg 拉小米云 CDN，失败还要重建会话）→ 这就是"一会有一会没有"的主要来源 |
| 方案 | ① token 加密存 DB（按设备）；② 后端通过 go2rtc HTTP API **动态注册/更新流**；③ 流地址从 DB 生成，不再读 yaml；④ 云端只在"首次接入/刷新 token/换设备"时使用；⑤ 本地流失败自动重注册，而不是层层 fallback；⑥ 监控墙加"流健康"指示 |
| 难度 | 中 |
| 工作量 | 2–3 天 |
| 收益 | 画面稳定性显著提升；小米云调用量下降一个数量级 → 封控风险同步下降 |

### 4.3 小米空开/插座本地控制（本地优先、云端兜底）

| 项 | 内容 |
|---|---|
| 现状 | 全部走小米云；`miio_lan` 是占位 |
| 方案 | 实现 MiIO/MiOT LAN 协议（UDP 54321，token + AES-128-CBC；MIIO 老协议 + MIoT spec 新协议）；token 通过云 API 一次性获取、加密入库（类似 Home Assistant 的做法）；控制链路改为 `本地直连 → 失败退云端`；电压/电流/功率/累计电量本地读取 |
| 难度 | 中偏高（协议细节 + 加解密 + 型号差异 + 状态批量读取） |
| 工作量 | 3–5 天 |
| 收益 | 云挂了/封控了/断外网，**本地仍能断电和读电量**；轮询改成本地后云端请求大幅减少 |

### 4.4 涂鸦系空开/计量插座（市面常见，性价比高）

| 项 | 内容 |
|---|---|
| 现状 | `tuya_local` 占位 |
| 方案 | 实现涂鸦本地协议（TCP 6668，local key + AES；tinytuya 协议），支持开关 DP、电量统计 DP；local key 在设备配网时从涂鸦云一次性抓取（工具化） |
| 难度 | 中 |
| 工作量 | 3–4 天 |
| 收益 | 可以买几十块一个的涂鸦计量空开/插座，**不再被小米生态绑定**；也是降低小米账号风险的手段（设备分散到不同生态） |

### 4.5 温湿度等传感器 / 其他设备

| 项 | 内容 |
|---|---|
| 现状 | 无字段、无类别、无 UI、无历史存储 |
| 方案 | ① DB：`Device.capabilities Json`、新增 `DeviceTelemetry(id, deviceId, metric, value, unit, ts)` + 索引；② 类别扩展：`temp_humidity_sensor`、`door_sensor`、`water_leak_sensor`、`energy_meter`、`gateway` 等；③ 接入：各 Provider 上报 + **MQTT 通用入口**（ESPHome / Tasmota / Home Assistant / 自研网关都能接）；④ 前端：房间详情加"环境数据"卡片、趋势图复用现有 ECharts；⑤ 告警：阈值规则（温度过高/过低、湿度过高） |
| 难度 | 中（模型改动会影响现有页面，需要迁移） |
| 工作量 | 4–6 天（不含具体硬件联调） |
| 收益 | 从"电费管理"升级成"公寓设备管理平台"，温湿度/门磁/水浸都能进；也为将来接 Home Assistant 留了路 |

### 4.6 MQTT / Home Assistant 桥接（可选，性价比高）

如果你已经在用 Home Assistant（或者将来用），不必把所有厂商协议都重写一遍：加一个 MQTT 接入器，订阅 HA 的 state topic（或直接调 HA REST API），就能把各种传感器/开关统一接进来。工作量 2–3 天，收益是"任何能进 HA 的设备都能进你的平台"。

### 4.7 小米云稳定性 / 账号封控专项

**结论先说**：不能保证小米永不风控（黑盒策略），但可以把影响从"整个系统不可用"降级为"云数据暂缓、本地控制正常"。可做的事：

1. **降频**：定时同步 60 秒一次可配置（现在 60 秒 + 页面 15 秒阈值叠加）；相机账号只在监控墙/回放页打开时拉设备列表。
2. **合并**：设备列表 + 批量属性已经是一次请求，保持；避免每个页面各自触发全量刷新。
3. **本地优先**：空开控制/读表走 MiIO LAN；摄像头走 go2rtc 本地 P2P。云端只做兜底 → 云端请求量可降 80%+。
4. **会话治理**：Redis 持久化已做；补齐 401 自动恢复（限频 + 指数退避 + 告警）；避免"失败就反复重登"。
5. **出口 IP 固定**：生产走固定出口（不要手机热点/频繁换网络登录同一账号）；Cloudflare Quick Tunnel 不影响小米请求的源 IP，但服务器本身换网络会影响。
6. **账号隔离**：目前已是 main（电表）+ camera（相机）双账号，保持；不要在同一账号上同时做高频读和写控制。
7. **人工兜底**：验证码/安全验证状态在 UI 明确提示（现在已有 authStatus），而不是静默掉线。
8. **风控后的行为**：云端失败时明确降级（显示"云端离线/本地可控"），不要每 5 秒重试刷屏。

### 4.8 能做 / 不能做的边界（避免预期落差）

| 能做 | 不能做 / 不建议 |
|---|---|
| 局域网摄像头（ONVIF/RTSP）完全本地直播、录像、上墙 | 纯小米摄像头"首次配对"仍需一次小米云授权（拿 token/激活 P2P） |
| 小米设备拿到 token 后本地控制、本地读电量 | 完全摆脱小米 App：小米部分设备（如需要云端密钥的加密设备）本地协议不公开 |
| 涂鸦/HTTP/Modbus/MQTT 设备完全本地 | 闭源私有协议的设备（部分品牌摄像头）无法逆向，只能走其云或 ONVIF（若有） |
| 温湿度等传感器接入与告警 | 现成的小米温湿度屏，若只支持 BLE/米家加密协议，需要网关或 HA 中转，工作量大 |
| UI 保留现有风格，只做结构拆分与增量页面 | 不建议照搬 Home Assistant 的 UI（你也说了不喜欢），只借鉴其"集成/实体/能力"的架构思想 |

```
└─ package.json / tsconfig.base.json / .gitignore / README.md / CHANGELOG.md
```

**"每个系统分开"的落地方式**：
- 前端系统 = `apps/web`（自己的 package.json、tsconfig、vite 配置、Dockerfile）；
- 后端 API 系统 = `apps/api`（自己的 package.json、Prisma、Dockerfile）；
- 设备接入系统 = `packages/core` + `packages/provider-*`（每个 Provider 一个包，接口统一、可单测）；
- 流媒体系统 = `packages/streaming`（唯一允许碰 ffmpeg/go2rtc 的地方）；
- 契约系统 = `packages/contracts`（只放类型，禁止运行时依赖）；
- 部署系统 = `infra/`（docker/compose/nginx/脚本）；
- 数据 = `data/`（gitignore）。

依赖方向（必须单向，否则又会变乱）：
`web → contracts`；`api → contracts, domain, core, provider-*, streaming`；`provider-* → contracts, domain, core`；**业务域禁止 import 具体 Provider，只依赖 `core` 接口**。

### 5.3 设备接入层抽象（升级的技术核心）

新增统一接口（示意）：

```ts
// packages/core/src/provider.ts
export interface DeviceProvider {
  id: string;                     // 'xiaomi-cloud' | 'xiaomi-local' | 'tuya-local' | 'onvif' | 'http' | 'modbus' | 'mqtt'
  displayName: string;
  /** 发现设备（扫描/云端列表/配对） */
  discover(ctx: DiscoverContext): Promise<DiscoveredDevice[]>;
  /** 读取状态与遥测（在线、开关、功率、温度…） */
  read(device: DeviceRef): Promise<DeviceReading>;
  /** 控制（开/关/亮度/…） */
  control(device: DeviceRef, cmd: DeviceCommand): Promise<ControlResult>;
  /** 视频源（摄像头类） */
  getStream?(device: DeviceRef): Promise<StreamSource | null>;  // rtsp/hls/webrtc
}
```

配套模型：
- `DeviceCapability`：`switch` / `meter` / `camera` / `sensor.temperature` / `sensor.humidity` / `sensor.contact` / `sensor.leak` …
- `DeviceReading`：`{ online, power?, energyKwh?, voltage?, current?, metrics: Record<string, number> }`
- DB 迁移：`Device.provider`、`Device.capabilities Json`、新增 `DeviceTelemetry` 时序表；保留现有字段兼容旧页面。

## 6. 参考开源项目对照（等你发链接后可精确对照）

按你描述的"类似、功能更多、能加温度等设备、UI 不喜欢"，**大概率是 Home Assistant**。先列候选与可借鉴点：

| 项目 | 与你的项目关系 | 可借鉴什么 | 不建议照搬什么 |
|---|---|---|---|
| **Home Assistant**（家庭助理） | 最像你说的"功能更多的开源项目" | Integration/Entity/Device 三层模型、Capability 抽象、多协议接入（ONVIF/Tuya/MQTT/ESPHome）、自动化与告警、组件化前端 | 它的 UI/UX（你不喜欢）、YAML 配置方式、过度通用导致的重配置 |

| **python-miio** | MiIO 局域网协议参考 | UDP 54321 握手、token 加解密、设备状态解析 | 语言不同，移植即可 |
| **go2rtc**（已在用） | 摄像头本地流桥 | 动态流注册 API、xiaomi:// P2P 源、多种摄像头协议源 | 不要手改 yaml，改成 API 注册 |
| **MediaMTX**（可选替代 go2rtc 的一部分） | RTSP/HLS/WebRTC 服务器 | 录像、路径管理、多摄像头并发 | 引入前评估与 go2rtc 的职责重叠 |
| **Frigate**（可选） | 摄像头 AI 侦测/录像 | 智能侦测录像、事件、硬件加速 | 对公寓管理可能过重，可只参考录制/事件模型 |
| **tinytuya / localtuya** | 涂鸦本地协议参考 | 涂鸦 6668 协议、local key、DP 映射 | — |
| **ESPHome / Tasmota / OpenBeken** | 自制/刷机传感器与空开 | MQTT 接入标准、计量芯片数据格式 | 需要硬件配合 |
| **ONVIF 设备管理库（如 `onvif-zeep`）** | 局域网摄像头发现 | WS-Discovery、GetStreamUri、海康/大华 RTSP 模板 | Python 库仅作协议参考 |
| **ThingsBoard / IoTSharp** | 通用 IoT 平台 | 遥测模型、规则引擎 | 对你的规模过重，不建议更换底座 |

**对照结论**：你的项目在"能源运营"（限额断电、自动恢复、电费统计、审计）上比通用开源平台更贴近公寓场景；通用平台的强项在"设备接入广度"。**正确策略是：保留自己的业务内核与 UI，只借鉴它们的"接入层 + 能力模型"思想，按第 4 节逐步扩展协议。** 你发链接后，我可以逐页对照列出"哪些功能值得抄、怎么落到这个项目里"。
